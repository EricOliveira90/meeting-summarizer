### 1. The "Heads-Up" Status Bar

Before the menu options appear, the user must see the **System State**. This anchors their expectations (e.g., "Don't expect a summary right now, the server is down"). Behind the scenes, the CLI runs a fast reconciliation (`cleanPhantomFiles`) to ensure these numbers perfectly match the files currently on your hard drive.

Plaintext

```

┌─────────────────────────────────────────────────────────────┐
│  SERVER: 🟢 Online (12ms)   |   LOCAL QUEUE: 3 items        │
│  READY TO FETCH: 1          |   NEEDS ATTENTION: 0          │
└─────────────────────────────────────────────────────────────┘


```

* **Server Status:** Real-time "heartbeat" check upon app launch via `api.ts`.
* *States:* 🟢 Online, 🔴 Offline, 🟡 Reconnecting.


* **Local Queue:** Recordings finished but not yet acknowledged by the server (`WAITING_UPLOAD`).
* **Ready to Fetch:** Jobs that the server finished processing, ready to be saved locally and to Obsidian (`READY`).
* **Needs Attention:** Jobs that hit their max retry limit or encountered a fatal error (`ABANDONED`).

### 2. The Dynamic Main Menu

The menu options should be action-oriented. While the current implementation uses a static list, the target UX includes dynamic labels generated by querying `db.ts` that change based on the local state.

#### **A. [Record] Start Recording 🔴**

* *Always available, regardless of server status.*
* **UX Note:** Uses global hotkeys (`[M]` for mute, `[Enter]` to stop). When recording stops, the CLI immediately prompts for a Meeting Title, renames the file safely, and adds it to the database as `WAITING_UPLOAD`.

#### **B. [Sync] Sync & Summarize 🧠 (The Magic Batch Process)**

* *The "Magic Button".* This is powered by `syncManager.runFullSyncCycle()` and strictly executes the entire lifecycle in this exact order to prevent data loss:
1. **Auto-Ingest:** Scans the output folder for new, untracked media files. Prompts the user to title and configure AI options for them.
2. **Update States:** Polls the server to see if any `PROCESSING` jobs have finished (marking them `READY` or `FAILED`).
3. **Fetch Results:** Downloads completed summaries and transcriptions, saving them as local `.txt` files *and* rendering them into the configured Obsidian vault template.
4. **Push Pending:** Uploads any files marked `WAITING_UPLOAD` or retries jobs marked `FAILED` (if under the max retry limit).


* **Dynamic Labeling Target:**
* If everything is up to date: `Sync (Up to date)`
* If items are waiting: `Sync (2 Uploads | 1 Download)`



#### **C. [Jobs] View Processing Status (Planned)**

* A list view of the local audit log (`client-db.json`). This satisfies the need to know "what's happening."
* **Status States & Colors (chalk):**
* `WAITING_UPLOAD` (Cyan): Local only, ready to go.
* `UPLOADING` (Blue): Currently sending.
* `PROCESSING` (Purple): Server has it, transcribing/summarizing.
* `READY` (Green): Finished on server, waiting to be fetched.
* `COMPLETED` (Green/Dim): Successfully fetched and saved to disk.
* `FAILED` (Yellow): Intermittent tunnel/network error. Will retry on next sync (e.g., Retry 1/3).
* `ABANDONED` (Red): Fatal error (e.g., Bad API Key) or max retries hit.
* `DELETED` (Dark Gray/Strikethrough): User deleted the `.mkv` manually. Kept for audit history.



#### **D. [Library] Settings & Audio Setup ⚙️**

* **Settings:** Setup the configs (server IP/Port, API keys, paths).
* **Audio Setup:** Queries OBS directly to let the user select the active Microphone and Desktop Audio sources.

### 3. User Flow Scenarios

#### **Scenario A: The "Offline" Recording**

1. **User:** Opens tool. Status Bar shows `SERVER: 🔴 Offline`.
2. **Action:** User selects `Start Recording`.
3. **End:** User hits `[Enter]` to stop recording.
4. **System:** Prompts for Meeting Title, renames the `.mkv` file, and saves it to the local DB.
5. **Menu:** Updates to `Sync (1 Pending Upload)`.

#### **Scenario B: The "Magic Batch" Sync**

1. **User:** Opens tool later. Status Bar shows `SERVER: 🟢 Online`.
2. **Menu:** Shows `Sync (3 Pending Uploads | 2 Ready to Fetch)`.
3. **Action:** User hits `Sync`.
4. **Feedback:** The system polls active states, downloads the 2 finished files (saving `.txt` files to `summaries/` and `transcriptions/` directories, plus the Obsidian vault), and then uploads the 3 pending files.
5. **Result:** Status returns to `Sync (Up to date)`.

#### **Scenario C: The Drop-In (Auto-Ingestion)**

1. **User:** Manually copies an older recording (e.g., `legacy_meeting.mp3`) into the configured output directory using Windows Explorer.
2. **Action:** User opens the CLI and selects `Sync`.
3. **System:** `ingestion.scanDirectory()` detects the untracked file before doing anything else.
4. **Prompt:** The CLI pauses and asks the user for a Title, Language, and AI Template for the newly discovered file.
5. **Feedback:** After answering, the system renames the file, adds it to the queue, and seamlessly continues the rest of the sync process to upload it.

#### **Scenario D: The "Ghost File" (Reconciliation)**

1. **User:** Records a meeting, but deletes the `.mkv` from Windows Explorer before syncing.
2. **System (Boot):** Runs `cleanPhantomFiles()`. Detects the missing file.
3. **Jobs View:** The record is now safely marked as `DELETED` instead of crashing the app when `SyncManager` attempts to read the file stream.

#### **Scenario E: The Flaky Tunnel (Retry Logic)**

1. **System:** Attempting to upload a large meeting.
2. **Event:** The SSH tunnel drops mid-upload, throwing an `ECONNRESET` error.
3. **System:** Catches the transient network error. Marks job as `FAILED` (Retry 1/3) rather than `ABANDONED`.
4. **Action:** User hits `Sync` later when the connection is stable.
5. **System:** Successfully uploads the `FAILED` job and resets the retry counter back to 0.

### 4. Implementation Tip (Node.js/TypeScript)

To keep the codebase lean and maintainable for a single developer:

* Use **`inquirer`** for the menu, **`ora`** for batch-processing spinners, and **`chalk`** for color-coding states.
* Isolate all visual UI drawing into a dedicated `ui/cli-views.ts` file.
* Clear the console (`console.clear()`) and reprint the Status Bar header on every menu loop refresh. This makes it feel like a persistent, reactive app UI rather than a scrolling terminal log.
